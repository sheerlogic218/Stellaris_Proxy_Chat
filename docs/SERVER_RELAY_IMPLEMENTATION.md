# Proxy Chat: central bot + relay, implementation plan

This is the step-by-step plan for each section of
[SERVER_RELAY_DESIGN.md](SERVER_RELAY_DESIGN.md). Section numbers match the design doc.
Every step lists **what to build**, the **files**, the **tests**, and **when it counts as done**.

**Decisions it builds on:**
- the home server runs Pop!_OS;
- local self-host mode stays;
- the guild cap is 5;
- guild approval is through the server CLI only;
- the bot must be fully usable with no relay connected, for example to clean up claims between sessions.

**Sizes:** S is up to an evening, M is a few evenings, L is a week or more of evenings.

---

## Dependencies

| Where | Package | Why |
|---|---|---|
| core, server, relay | stdlib `sqlite3`, `json`, `hashlib`, `secrets` | No extra attack surface |
| server (`api`) | `aiohttp` | discord.py already depends on it, so it adds nothing new |
| server and relay | `cryptography` | Ed25519 sign and verify |
| server (`bot`) | `discord.py` (pinned, as now) | — |
| relay | `keyring` | Windows Credential Manager |
| relay HTTP | stdlib `urllib.request` with the default SSL context | Keeps the relay's dependencies to two packages |
| dev only | `pytest`, `hypothesis`, `pip-audit` | Tests, fuzzing, vulnerability scan |

- **Lock files:** each component gets its own `requirements/<component>.in` and a locked `requirements/<component>.txt` with hashes, generated by `pip-compile --generate-hashes`. Everything installs with `pip install --require-hashes`.
- **Python version:** the server images are pinned to the same minor version you develop on.

## §1 Architecture: split the code into core, relay and server  (M)

**Goal:** the same core logic runs in three places: local mode, the relay, and the server bot.

1. **Create `proxychat_core/`.**
   - Move `protocol.py` and `state.py` there unchanged. Leave a shim in `proxychat_bot/` for now so imports keep working.
2. **Abstract where events come from.** Add an `EventSource` interface in `proxychat_core/source.py`: `async def batches() -> AsyncIterator[list[SlotEvent]]`, where `SlotEvent = (slot_id, date, record)`.
   - `LocalLogSource(slot_id, log_path)` wraps today's `LogTailer` and `parse_line`. It's used by local mode.
   - `QueueSource(db)` reads `event_queue` (§7). It's used by the server bot.
3. **Abstract where state is saved.** `Store.save()` currently writes a file. Put a `StoreBackend` interface behind it:
   - `FileBackend(path)` is today's behaviour, for local mode;
   - `SqliteBackend(db, slot_id)` writes JSON into `slot_state`.

   `Store.to_json` and `Store.from_json` keep today's format, so migration is an import.
4. **Replace `watch_log()` in `bot.py`** with a loop over `EventSource.batches()`.

**Tests:** the existing `tests/test_core.py` and `tests/test_reconcile.py` pass after only import changes. Add a test that runs a recorded `game.log` through `LocalLogSource` and checks it gives the same `Store` as today.

**Done when:** `python -m proxychat_bot` (local mode) behaves exactly like `main` does today, and the tests are green.

## §2 Threat model → a security test suite  (M, built up alongside the other sections)

Every threat in the design gets at least one automated test, plus one manual check after
deployment. These go in `tests/security/` and are written **with** the feature they
protect, not afterwards.

| Threat | Test |
|---|---|
| Unauthenticated probing | Unknown path → 404 with an empty body. GET on a known path → 404. Missing headers → 401 without the body being parsed. This is checked with a mock that fails if JSON parsing is called. |
| Oversized or slow bodies | 17 KiB → 413. A body that trickles in for more than 5 s → connection closed. |
| Replay | The same signed request sent twice → the second gets 401. A timestamp ±61 s off → 401. |
| Forged or wrong key | Signature from another key → 401. Revoked key → 401. |
| Cross-tenant access | A key for guild A/slot 1 whose body names guild B or slot 2 → the event lands in A/1, or is rejected. The bot side ignores queue rows whose key no longer maps to that slot. |
| Hostile names | `@everyone`, `<@123>`, zero-width characters, 10 KB names, RTL override, newlines → sanitised or rejected (property tests with `hypothesis`). |
| Floods | Per-key and global rate limits → 429. The caps on call channels and moves per slot hold. |
| Pairing brute force | 11th attempt within a minute → 429. A used or expired code → 401. Codes are stored hashed. |
| Unapproved guild | Joining an unapproved guild → the bot leaves. Approving a 6th guild → refused by the CLI. |
| Dangerous Discord permissions | A guild where the bot role has Administrator → the slot is refused and the admin is told why. |

**Fuzzing:** `hypothesis` generates random record dicts and JSON bodies. The API must
only ever answer 2xx, 4xx or 429, never 500, and must never write a malformed row.

**Done when:** `pytest tests/security` runs in CI on every push.

## §3 Home server hardening on Pop!_OS  (L)

All files go in `deploy/`. Nothing is installed until the code from §1–§8 exists. The
host steps below can be done earlier.

### 3a. Host preparation (one-off, S)
1. **Install Docker Engine** from Docker's official apt repo, using the Ubuntu codename Pop!_OS is based on. Then enable it with `systemctl enable --now docker`.
2. **Configure the Docker daemon** in `/etc/docker/daemon.json`:
   ```json
   { "userns-remap": "default", "no-new-privileges": true, "live-restore": true,
     "log-driver": "local", "log-opts": { "max-size": "10m", "max-file": "3" } }
   ```
   `userns-remap` maps root inside containers to an unprivileged range on the host
   (`dockremap` in `/etc/subuid`). Bind-mounted data folders must be owned by that
   range (see 3c).
3. **Turn on automatic security updates:** `apt install unattended-upgrades`, then enable the security origin. This is separate from the Pop Shop desktop updates.
4. **SSH:** only over Tailscale SSH or the LAN, with key authentication and password login off. Funnel never touches SSH.
5. **Don't create a separate Linux user for this.** Docker's group membership is effectively root, so a separate user adds nothing over keeping it on an admin-only account. The protection comes from the container hardening below.

### 3b. Tailscale (one-off, S)
1. **Tailscale ACL policy** (admin console):
   - remove the default allow-all rule and write explicit rules for your existing devices;
   - add `tagOwners` for `tag:proxychat` and the `funnel` node attribute (snippet in `deploy/tailscale-acl-snippet.jsonc`);
   - add **no** rule with `tag:proxychat` as a source or destination.
2. **Auth key:** generate a **single-use, pre-authorised, tagged** (`tag:proxychat`) key. Store it in `deploy/secrets/ts_authkey` (mode 0400). Delete it once the node has joined, because the node's state persists in the `ts-state` volume.
3. **HTTPS certificates:** turn on HTTPS certificates for the tailnet. Funnel needs them.

### 3c. `deploy/docker-compose.yml` (M)
| Service | Image | Networks | Volumes | Notes |
|---|---|---|---|---|
| `ts` | `tailscale/tailscale:<pinned tag>@sha256:…` | `edge`, `ts_out` | `ts-state:/var/lib/tailscale`, `./ts-serve.json:/config/serve.json:ro` | `TS_USERSPACE=true`, `TS_SERVE_CONFIG=/config/serve.json`, `TS_EXTRA_ARGS=--advertise-tags=tag:proxychat`, auth key from the secret |
| `api` | built from `Dockerfile.api` | `edge` only (`internal: true`) | `./data:/data` | No secrets. Listens on `0.0.0.0:8080` inside `edge` only. |
| `bot` | built from `Dockerfile.bot` | `bot_out` | `./data:/data` | Secret `discord_token` at `/run/secrets/discord_token` |

- **Every service gets:** `user: "10001:10001"`, `read_only: true`, `tmpfs: [/tmp]`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `mem_limit`, `cpus`, `pids_limit: 128`, and `restart: unless-stopped`.
- **Networks:** `edge` has `internal: true`, so it has no route out. `ts_out` and `bot_out` are normal bridges with fixed subnets (for example `172.30.1.0/24` and `172.30.2.0/24`) so the firewall rules can target them.
- **`ts-serve.json`:** serves HTTPS 443 and proxies `/` to `http://api:8080`, with `AllowFunnel` true for `${TS_CERT_DOMAIN}:443`.
- **Data folder:** `./data` is owned by the remapped UID (`100000 + 10001` with the default subuid range) and is mode 0700.

### 3d. Dockerfiles (S)
- **Two stages:** a builder stage installs locked wheels with `--require-hashes`, and the final stage is `python:3.x-slim@sha256:…`. It copies only the venv and the app package, drops pip, and adds a non-root user 10001.
- **`api` and `bot` are separate images:**
  - `api` includes `proxychat_core` and `proxychat_server/api`;
  - `bot` includes `proxychat_core` and `proxychat_server/bot`, plus `admin_cli`.

  Neither image contains the other's code.
- **Health checks:** `api` answers `GET /healthz` **only on a second port bound to localhost inside the container**, so Funnel can't reach it. `bot` writes a heartbeat into the database, which `admin_cli status` reads.

### 3e. Host firewall (S)
- **`deploy/firewall-docker-user.sh`** sets up the `DOCKER-USER` chain:
  1. accept `ESTABLISHED,RELATED`;
  2. for sources in the `ts_out` and `bot_out` subnets, **drop** traffic to `10/8`, `172.16/12` (except the compose subnets), `192.168/16`, `100.64/10`, `169.254/16` and `fe80::/10`;
  3. return.
- **Applying it:** a systemd unit, `proxychat-firewall.service`, runs it with `After=docker.service` and `PartOf=docker.service`, so the rules come back after reboots and Docker restarts.
- **Why it's needed:** ufw on Pop!_OS does **not** see Docker's forwarded traffic, so these rules are the LAN block.

### 3f. Backups (S)
- **Nightly job:** a systemd timer, `proxychat-backup.timer`, runs `deploy/backup.sh` every night:
  1. `docker exec bot python -m proxychat_server.admin_cli backup /data/backups/tmp.db`, using the SQLite online backup API;
  2. `age -r <public key> -o proxychat-<date>.db.age`, then delete the plaintext copy;
  3. keep 14 copies and rsync them to an off-box target over Tailscale (your PC or a NAS).
- **The age private key never sits on the server.**
- **Restores:** test one once (step 7.4).

### 3g. Post-deploy self-test (S)
`deploy/selftest.sh`, run from **outside** the server, for example your PC with Tailscale off:
- `curl` an unknown path → 404, an unsigned POST → 401, an 17 KiB POST → 413, 40 quick unsigned POSTs → some 429s.

And run from the server:
- `docker exec api python -c "<connect to 1.1.1.1:443>"` → fails, because there's no route;
- `docker exec bot … <connect to your router's IP>` → fails, because of the firewall;
- `docker exec bot … <connect to discord.com:443>` → works;
- `docker exec ts tailscale ping <your PC>` → fails, because of the ACL.

**Done when:** every check in the self-test passes. Re-run it after every deploy change.

## §4 Relay ↔ server protocol (`proxychat_server/api`)  (L)

1. **`auth.py`:**
   - `verify(request_headers, body_bytes, db) -> RelayKey | None`. It builds the canonical string `POST\n<path>\n<time>\n<nonce>\n<sha256 hex>`, checks clock skew (60 s), checks the nonce against an in-memory TTL cache (120 s, capped at 100k entries), checks the key status in the database, and verifies the Ed25519 signature.
   - Comparisons are constant-time where it applies, and every failure returns one generic error.
2. **`app.py` (aiohttp):**
   - `client_max_size=16*1024`;
   - a middleware order of: global unauthenticated rate limit → method and path allowlist → `Content-Length` and `Content-Type` checks → reading the body with a 5 s timeout → `auth.verify` → per-key rate limit → handler;
   - no `access_log` lines with IPs: the log format has the key id, path, status and time only;
   - custom 404 and 500 handlers that return empty bodies.
3. **Routes:**
   - `POST /v1/pair`: rate-limited; looks up `sha256(code)`; does the "unused and not expired → mark used" step in **one transaction**; validates the public key (32 raw bytes, base64url); limits the label to 32 printable characters; returns `{key_id}`.
   - `POST /v1/events`: validates with `schema.py`, then in one transaction:
     - drops records at or below the last seq for `(slot, launch)`;
     - inserts the new ones into `event_queue`;
     - renews the lease;
     - writes the new last seq.

     It returns `{ok, acked, lease, min_relay_version}`.
   - `POST /v1/heartbeat`: lease renewal only.
   - `POST /v1/release`: drops the lease when the relay shuts down cleanly. This is a small addition to the design.
4. **`schema.py`:**
   - one hand-written validator per record type (no generic deserialiser), built from the same field rules as `protocol.py`;
   - name sanitising shared with the bot through `proxychat_core/names.py` (§6).
5. **`ratelimit.py`:** in-memory token buckets for global unauthenticated requests, pairing, per-key requests and per-key records. Because they're in memory, they reset on restart, which is acceptable.
6. **Maintenance flag:** the API reads `settings.maintenance` from the database (cached for 5 s) and answers 503 for everything except `/healthz`.

**Tests:** the §2 rows for probing, bodies, replay, keys, pairing, floods and fuzzing, run
with `aiohttp.test_utils` against a temporary SQLite database.

**Done when:** the API runs locally (`python -m proxychat_server.api --db test.db`) and passes `tests/security` and `tests/api`.

## §5 Tenancy: guilds, slots and sessions in the bot  (L — the biggest refactor)

Today `ProxyChatBot` assumes one `cfg.guild_id`, one category and one `store`. Here's how that changes:

1. **A `Slot` runtime object** in `proxychat_server/bot/slots.py`:
   - fields: `slot_id`, `guild_id`, `category_id`, `commands_channel_id`, `store`, `processor`, `dirty`, and the per-slot call-channel timers;
   - built from the `slots` table at startup, and reloaded when `/proxychat slot add` or `remove` runs.
2. **Thread `slot` through the bot.** Every method that touches `self.cfg.guild_id`, `self.cfg.category_id` or `self.store` takes a `slot` instead:
   - `reconcile*`, `ensure_category`, `ensure_commands_channel`, `arrange`, `cleanup*`;
   - `handle_join`, `handle_home`, `handle_galcom`, `handle_federation`, `handle_call`;
   - `announce`, `post`.

   `ours()` and `in_category()` check `channel.category_id == slot.category_id` and
   `channel.id in slot.store.owned`.
3. **Pick the slot from what happened:**
   - **queue events** carry `slot_id`;
   - **voice state updates** use the slot whose `category_id` matches the channel's category;
   - **slash commands** use the slot of the category of the channel they're run in, otherwise an explicit `slot:` option (autocomplete lists that guild's slots), otherwise the guild's only slot.
4. **Run reconciliation per slot:** `reconcile_loop` goes through the slots marked dirty, and each slot has its own lock, so two games never block each other.
5. **Lease awareness:**
   - the bot reads `leases` only to show `/proxychat status` ("hosted by <label>, last seen 12 s ago");
   - the bot never needs a lease to act, so **commands work with no relay connected**.
6. **Local mode:** one synthetic slot built from `config.toml` (`guild_id`, `category_id`), with `FileBackend` and `LocalLogSource`. The same code path runs, with no SQLite needed.

**Tests:** update `tests/test_reconcile.py` to build a `Slot`. Add tests that:
- with two slots in one guild, events for slot 1 never create or delete channels in slot 2's category;
- with two guilds, the same;
- a command run in slot 2's category affects only slot 2.

**Done when:** local mode passes everything, and a two-slot test guild works with `QueueSource` fed by a test script.

## §6 Discord side  (M)

1. **Approval gate** (`bot/guards.py`):
   - `on_guild_join`: if the guild isn't approved, try to DM the inviter (taken from the audit log if the bot can see it, otherwise skipped), then `guild.leave()`;
   - on startup and every 10 minutes, leave any unapproved guild still on the bot's list;
   - write an audit row and alert the owner.
2. **Permission guard:**
   - extend the existing `check_permissions()` so it **refuses** a slot when the bot's guild-level permissions include Administrator, Manage Server, Manage Roles, Manage Channels, Manage Webhooks, Ban or Kick;
   - check on setup, on `on_guild_role_update` and `on_member_update` for the bot, and every hour;
   - a refused slot is frozen (no Discord actions), and the guild's admins are told in its commands channel or by DM.
3. **Commands:**
   - drop the per-guild `copy_global_to(...)`/`sync(guild=...)` in server mode and call `tree.sync()` once globally;
   - local mode keeps per-guild sync, because it shows up instantly;
   - new `/proxychat` subcommands: `setup`, `slot add`, `slot remove`, `host` (gives a pairing code, ephemeral), `relays`, `relay revoke`, `lease release`, `claims clear`, `session end`;
   - existing subcommands kept: `status`, `assign`, `unassign`, `cleanup`, `resync`.

   Everything is ephemeral and every admin action writes an `audit_log` row.
4. **Admins per guild:** `is_admin()` reads `admin_role_ids` from the `guilds` table instead of `cfg`, and `/proxychat setup` sets them. The approval CLI is still the only way a guild gets in.
5. **Mentions:** pass `allowed_mentions=discord.AllowedMentions.none()` to the `Client` constructor, so it applies to every message. Keep the per-message ones too.
6. **`proxychat_core/names.py`:**
   - `clean_name(s, limit) -> str`: NFC-normalise, drop the `Cc`/`Cf` Unicode categories (control and format characters, which includes zero-width and RTL overrides), drop `@#<>*_~|\`` characters, collapse whitespace, truncate, fall back to `Empire <id>`;
   - used by the API schema **and** by the bot before naming channels or sending DMs.
7. **Between-session commands:**
   - `claims clear`: clears all claims for the slot's current campaign, after a confirm flag like the existing `cleanup`;
   - `session end`: archives the campaign (marks it ended in `slot_state`), deletes its channels through the existing cleanup path, and takes an option to also clear claims.

**Done when:** all of this works in your test server under local mode first, then in server mode.

## §7 Data  (M)

1. **`proxychat_server/db.py`:**
   - `connect(path)` sets `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000` and `synchronous=NORMAL`;
   - migrations are numbered SQL strings applied by `PRAGMA user_version`;
   - migration 1 creates the tables in design §7.1, plus `settings(key, value)` and `launch_seq(slot_id, launch, last_seq)`.
2. **Queue consumption** (`bot/queue.py`):
   - poll every 0.5 s with `SELECT … ORDER BY id LIMIT 500`;
   - for each row, **validate again** (design §7.3) and check that the key is active and bound to that slot;
   - then `processor.feed` it; in **one transaction** save `slot_state` and delete the rows; then mark the slot dirty;
   - Discord actions happen afterwards, and reconciliation is idempotent, so a crash can't corrupt anything.
3. **Retention job** (`bot`, every hour):
   - purge guilds removed for more than 7 days, ended sessions older than 30 days, `audit_log` rows older than 90 days, expired pairing codes, and queue rows older than 1 day (stuck rows);
   - write one audit row summarising the purge counts.
4. **`proxychat_server/admin_cli.py`** (run with `docker exec bot python -m proxychat_server.admin_cli …`):
   - `guild approve <id> [--max-slots N]`: refuses a 6th guild (`settings.max_guilds=5`);
   - `guild list|freeze|unfreeze|remove`;
   - `relay list [--guild]`, `relay revoke <key_id>`, `relay revoke-all`;
   - `maintenance on|off`;
   - `audit tail [-n]`;
   - `status` (bot heartbeat, slots, leases, queue depth);
   - `backup <path>`;
   - `import-state <guild_id> <category_id> <state.json>`, for §11 migration.

   Every command writes an audit row with the actor set to `cli`.
5. **`PRIVACY.md`** in the repo root: what's stored, how long it's kept, and how a guild owner can have it deleted (remove the bot, which purges the data after 7 days, or ask you).

**Tests:** migrations from an empty database, queue crash safety (simulate an exception
between the feed and the commit), each retention rule, and the CLI cap of 5 guilds.

## §8 The relay (`proxychat_relay`)  (M)

1. **`config.py`:** `%APPDATA%\ProxyChatRelay\relay.toml` holds `server_url`, `key_id`, `label`, `log_path` (defaulting to today's `DEFAULT_LOG`) and `poll_seconds`. It holds no secrets.
2. **`keys.py`:**
   - generate an Ed25519 key;
   - keep the private key in `keyring` under service `proxychat-relay` and username `<key_id>`;
   - the private key is never written to disk or logs, and never printed.
3. **`client.py`:**
   - signs with the same canonical string as `auth.py`, from shared code in `proxychat_core/signing.py`;
   - sends over `urllib.request` with the default SSL context, accepting `https://` URLs only (refusing plain `http` unless `--insecure-local` is used for tests against localhost);
   - retries with exponential back-off (1 s → 60 s, with jitter); honours 429 and 503;
   - stops and tells the user on 401 ("this relay was revoked, pair again") and on `min_relay_version` ("please update");
   - handles `lease: denied` by showing "Slot is hosted by someone else" and retrying every 60 s;
   - releases the lease on Ctrl+C.
4. **`run` loop:**
   - `LogTailer` → `parse_line` → turn each record into a dict, then batch every 1 s or at 200 records;
   - `launch` = sha256 of the first 4 KiB of `game.log`, so it stays the same across relay restarts within one game launch;
   - `seq` = the record's position in the file;
   - unacknowledged records are kept in memory (up to 5,000), because a relay restart replays the log anyway.
5. **`cli.py`:** `pair <server_url> <code> [--label]`, `run`, `status`, `forget` (removes the key from keyring and the config). Add `start_relay.bat`.
6. **Packaging:**
   - a release zip with `setup_relay.bat` (creates a venv and runs `pip install --require-hashes -r requirements/relay.txt`);
   - an optional PyInstaller `.exe` built in GitHub Actions, with SHA256 sums and `actions/attest-build-provenance`.

**Tests:** signing matches what the server verifies (shared test vectors), the launch id
is stable, back-off and lease handling against a fake server, and no secret appears in
logs (a test that captures logs and greps them for the key bytes).

## §9 Operations and kill switches  (S)

1. **Owner alerts:** set `owner_user_id` in the server config (not a secret). The bot DMs you when:
   - an unapproved guild tries to join;
   - there are more than 20 auth failures in an hour (the API writes counters into `settings`, and the bot checks them every 5 minutes);
   - a relay is paired or revoked;
   - a slot is refused for dangerous permissions;
   - a backup fails (written by `backup.sh` through the CLI).
2. **Runbook:** `deploy/RUNBOOK.md` covers each row of design §9 as copy-pasteable commands:
   - Funnel off/on;
   - maintenance on/off;
   - revoking a key or all keys;
   - freezing a guild;
   - Discord token rotation (reset it in the portal → write the secret file → `docker compose up -d bot`);
   - restoring from backup.
3. **Updates:**
   - `.github/dependabot.yml` for pip, Docker and GitHub Actions;
   - CI (`.github/workflows/ci.yml`) runs the tests, `pip-audit` and the image build on every push;
   - on the server, `docker compose pull && docker compose build --pull && docker compose up -d` once a week or when flagged.

## §11 Build order and milestones

| # | Milestone | Sections | Outcome you can see |
|---|---|---|---|
| M1 | Core split | §1, start §2 | Local mode is unchanged, the tests are green |
| M2 | Multi-slot bot (local mode) | §5, §6 (guards, names, mentions, new commands) | Test server: two slots and the between-session commands work |
| M3 | Database and admin CLI | §7 | The bot runs on SQLite. The guild cap and approval work from the CLI. |
| M4 | API | §4, §2 security tests | The API passes the security suite locally |
| M5 | Relay | §8 | Relay on your PC → API and bot on your PC (all local) → test server works |
| M6 | Home server deploy | §3, §9 | Pop!_OS stack is up, the self-test passes, Funnel is live, the test server works through the relay |
| M7 | Migrate the main server | §7 `import-state` | Stop the local bot (**the same token must never run twice**), import `state.stellaris-server.json` as slot 1, volunteers pair relays, one game played on the new setup |
| M8 | Docs and release | §10 | Guides, `SECURITY.md`, `PRIVACY.md`, release zip, optional relay `.exe` |

**Notes:**
- **Staging:** your test server (the guild in `config.toml`) becomes approved guild #2 and the place where every change is tried first.
- **Same bot:** the central bot uses the **same Discord application and token** as today, so it already owns the main server's channels and has its category permissions. The `import-state` step keeps everyone's claims.
- **Order:** each milestone ends with a commit on `server-relay`. Nothing reaches `main` until M7 has worked through one real game.
